# E-9 加难缺陷（S7-hard）结果

> 本次花费 **¥11.53**（37 次调用 / 128,583 输入 / 72,091 输出），累计 **¥272.90**。
> 模型 deepseek-chat，`PARALLAX_MAX_EVIDENCE_PER_CALL` 按臂显式设定（见下表），全部 0 丢批、
> 全部 `stop_reason=max_rounds_reached`。

## 1. 设计与对照

S7-hard 用的是**与 `p1-subsample/S4` 逐字节相同的 26 文件语料**，只把缺陷换掉：

| | S4（易） | S7-hard（难） |
| --- | --- | --- |
| 文件 | 26 个 | 26 个（同一份） |
| 缺陷 | 12 条，`semantic_cache.py` 里 110~167 行密集 4 条 | 5 条，两两相距 ≥ 25 行 |
| 类别 | 校验缺失、key 少字段、截断方向… | 跨文件不一致、边界条件、无显眼标记的语义错 |

构造与验真见 `p0-slices/S7-hard/README.md`：干净版 17 条测试全绿，注入版恰好 H1–H5 五条红。

## 2. 核心发现：自动打分高估了召回，最多 2 条

`tools/score.py` 的口径是「同文件 + 行距 ≤ 25 + `stance=defect`」，一对一贪心。
在缺陷密集的 S4 上这个口径已经偏高；S7-hard 里我把缺陷间距拉开到 ≥ 25 行，
**但一条落在两个缺陷之间的无关 claim 仍会「借」到命中**。

逐条人工裁定后（明细见 §3）：

| 臂 | 配置 | 自动打分（口径内） | **人工裁定** | 高估 |
| --- | --- | ---: | ---: | ---: |
| `no_peers_all_evidence` | 3 读者，每人读 9 个文件 | 1/5 | **1/5** | 0 |
| `blind_no_coverage` | 3 读者，每人读 9 个文件 | 5/5 | **3/5** | +2 |
| `sharded_shared` | 3 读者读全 26 | 5/5 | **4/5** | +1 |
| `sharded_blind` | 3 读者读全 26 | 5/5 | **4/5** | +1 |
| `blind_no_coverage` | 1 读者，批 6，读全 26 | 5/5 | **3/5** | +2 |
| `blind_no_coverage` | 1 读者，批 13，读全 26 | 4/5 | **3/5** | +1 |

> **这一条比「缺陷难不难」更重要**：所有「召回贴天花板」的数字都是宽松口径下的上界。
> S4 的 11/12、10/12 同样应当被当成上界，而不是精确值。E4 的人工核实（`E4-VERIFICATION.md`）
> 之前只做了 1 片，现在有了第二个独立证据点：**同一批 claim 在严格口径下少 1–2 条**。

## 3. 逐条裁定

`✓` = 有 claim 明确描述该缺陷且 `stance=defect`；`✗` = 无，或看到的 claim 是别的问题；
`✗(判掉)` = 有 claim **准确指出**了这处，但被自己判成 `not_a_defect`。

| 缺陷 | 类别 | 集中(9文件) | 分散(9文件) | 读全·共享 | 读全·隔离 | 单Agent·批6 | 单Agent·批13 |
| --- | --- | :-: | :-: | :-: | :-: | :-: | :-: |
| h1 排序方向反了 | 无标记语义错 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| h2 滑窗上界多减 1 秒 | 边界条件 | ✗ | ✗ | ✓ | ✓ | ✓ | ✓ |
| h3 余弦丢维度守卫 | **跨文件不一致** | ✗ | ✓ | ✓ | ✓ | ✓ | ✗ |
| h4 阈值 `>=`→`>` | 边界条件 | ✗(判掉) | ✗ | **✗(判掉)** | **✗(判掉)** | **✗(判掉)** | **✗(判掉)** |
| h5 库存 `<=0` 拒绝售罄 | 不变量被收紧 | ✗ | ✓ | ✓ | ✓ | ✗(判掉) | ✓ |
| **合计** | | **1/5** | **3/5** | **4/5** | **4/5** | **3/5** | **3/5** |

### h4 是本次最值得记录的一条

六条臂**全部**在 `semantic_cache.py:140` 附近留下了 claim，**全部**准确写出「用的是严格大于」，
**全部**判成 `not_a_defect`。理由几乎一致：

> 「阈值边界行为与文档『低于阈值视为未命中』一致」

这是把「低于阈值 → 未命中」读成了「等于阈值 → 未命中」。规格原文是
「低于阈值视为未命中」，即 $s \ge \tau$ 才命中，`>` 多排除了 $s = \tau$ 这一个点。

所以 h4 的失败**不是没看见，是不敢报**——在宽松口径下这被记为「命中」，
在严格口径下是「漏检」。**「召回」这个词在本项目里同时混进了「看到」和「判定」两件事。**

> 公平性说明：h4 的缺陷性依据只有模块 docstring 那一句，原项目的
> `test_phase4_cache.py`（24 条）在两版代码上都全绿，**没有测试钉住这个边界**。
> 因此 h4 属于「规格欠定」类缺陷，单列，不与另外 4 条合并计分。

## 4. 结论

### 4.1 「是我们不行还是题目太简单」——两者都不是，是**量尺太松**

- 换难缺陷后，读全配置仍然拿到 4/5，说明**方法本身没有撞墙**；
- 但把自动打分换成逐条裁定后，同一批运行从 5/5 掉到 3/5，说明**之前的「贴天花板」
  有相当一部分是 25 行容差借来的**；
- 因此正确的表述不是「题目太简单所以召回 100%」，也不是「我们能力不足」，
  而是**「宽松口径把上界当成了点估计」**。

### 4.2 臂间排序在难缺陷上不变

| 配置 | S4（易，宽松口径） | S7（难，严格口径） |
| --- | ---: | ---: |
| 读全·隔离 `sharded_blind` | 11/12 = 92%（`p5-e3`） | 4/5 = 80% |
| 读全·共享 `sharded_shared` | 10/12 = 83%（`p5-e3b`） | 4/5 = 80% |
| 读全·不切片 `blind_full` | 12/12 = 100%（`p5-e3`，27 次调用） | 未跑 |
| 分散（覆盖 26/26） | 9~10/12 = 75~83% | 3/5 = 60% |
| 单 Agent 分批 | 10/12 = 83%（`p6-single`） | 3/5 = 60% |
| 单 Agent 单上下文 | 6/12 = 50%（`p6-single-context`） | 3/5 = 60% |
| 集中（每人只读 9/26） | 3/12 = 25%（`p4-chat`） | 1/5 = 20% |

> ⚠️ **同一配置重复跑会变**：`blind_no_coverage`（3 读者、每批 6）在 S4 上
> `p5-e3` 得 **9/12**、`p4-chat` 与 `p6-single` 得 **10/12**。单次运行 ±1 条是常态，
> 所以上表所有 S4 数字都应读作「点估计 ± 1 条」，而不是精确值。

- **读全 > 分散 ≈ 单 Agent > 集中**，两套难度下排序一致 → 机制结论稳健。
- 唯一反转：单上下文在难题上相对变好（50% → 60%），因为难缺陷分布在 4 个文件里，
  单上下文一次投喂也未必漏；样本仅 5 条，不足以主张。

### 4.3 共享仍然不给质量收益

读全时共享 4/5 = 隔离 4/5，与 S4/E3b 的结论一致：
**共享同伴结论不带来召回收益，只吃掉独立性（K\* 降、冗余率升 5/5）。**

### 4.4 边界类缺陷是当前最薄弱的环节

h2/h3 各只有 4/6 臂真正报出；h4 零臂报出。而 h1（排序反了）、h5（`<=0`）几乎人人都能看出。
**「一个字符的比较符/偏移」比「一整段逻辑反转」难得多。**

## 5. 限制

1. **n=5 条缺陷，1 个切片**。20%/40% 这类比例的置信区间极宽，只能做方向性判断。
2. **5 条缺陷的难度是自己造的**，不代表真实代码库里缺陷难度的分布；作者偏见无法完全排除。
3. h4 规格欠定，已单列。
4. 严格口径的人工裁定由单人完成，未做双人复核。
5. 仍是采样子语料，绝对召回率不可与全量运行比较。
