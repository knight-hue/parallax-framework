# E-3 公平成本对比（p8-fair）

> 本次花费 **¥2.22**（6 次调用 / 27,105 输入 / 13,856 输出），累计 **¥271.85**。
> 切片 `p1-subsample/S4`（26 文件 / 12 条缺陷），模型 deepseek-chat，`max_evidence_per_call=12`，
> 两臂均 0 丢批、0 失败、`stop_reason=max_rounds_reached`。

## 要修正什么

之前的「多 Agent 贵 43%」是在**批大小 6** 下算的：

| 臂 | 批大小 6 时的调用数 |
| --- | ---: |
| 单 Agent（1 读者读全 26） | 5 |
| 3 Agent 分散（每人 9 个文件） | 6（每人 2 批） |

26 个文件除以 6 是 4.33 批，除以 9 也是 1 批但**每个 Reader 都要多起一轮**。
**这是批次取整造成的，不是架构成本。** 把批大小提到 12（≥ 每人分到的 9 个文件），
两臂都恰好 1 批 → 都恰好 3 次调用，取整项消失。

## 结果

| 臂 | 调用 | 输入 token | 输出 token | 总 token | 召回 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单 Agent（1 读者，批 12） | 3 | 13,779 | 6,724 | 20,503 | **8/12** |
| 3 Agent 分散（每人 9 文件，批 12） | 3 | 13,326 | 7,132 | 20,458 | **9/12** |
| 差 | 0 | −3.3% | **+6.1%** | **−0.2%** | **+1 条** |

## 结论

1. **在调用次数与读取量对齐后，分散的架构成本约为零**：总 token 少 0.2%，
   输出 token 多 6.1%（多一轮 Reader 的开销），输入 token 反而少 3.3%（每人批更短）。
2. **「贵 43%」这个数字不能再用**，它测的是批大小 6 下的取整，不是架构差异。
3. 同等成本下分散多查出 1 条（8 → 9），与 E1 的方向一致，但 n=1 切片，只能算方向性。
4. **批大小本身独立影响召回**：批 6 时单 Agent 10/12、分散 10/12；批 12 时 8/12、9/12。
   批变大后两臂都掉——再次印证瓶颈在单次调用的输出容量，不在 Agent 数量。

## 限制

- n=1 切片、单次运行，±1 条的波动与观察到的差异同量级。
- 召回仍是 25 行容差口径（宽松上界），见 `METRIC-SENSITIVITY.md`。
- 未做重复运行估方差（E-8 仍未做）。
