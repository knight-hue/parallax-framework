更新：2026-10-28。配套：[作品介绍.md](作品介绍.md)、[证据索引.md](证据索引.md)、[演示视频脚本.md](演示视频脚本.md)。

## 一、三档讲法

### 30 秒版（评委路演）

> Parallax 是一个面向研发团队的代码审查协作平台。它解决的问题不是「模型不会提问题」，而是「多个同源模型说了一样的话，我们凭什么信」。平台侧用 Java + MySQL + RabbitMQ 做可靠任务、原子预算和人工审批；引擎侧用独立证据装配 + 三条抗从众控制面，把每条结论绑定到证据指针，把争议保留下来交给人。所有数字都能在仓库 `eval/` 里复现。

### 3 分钟版（结构化）

1. **问题**：同源模型错误高度相关（ICML 2025），信息分散任务上多智能体只有 30.1% 而单智能体有 80.7%（HIDDENBENCH）。多智能体的收益来自信息不对称，不来自人数。
2. **做法**：盲读分区（Reader 互不可见）+ Claim 账本（源指针/极性/独立支持）+ 规则聚合（不投票）+ 覆盖率驱动补检（派新身份 Reader）。
3. **本轮新增**：结论剥离仲裁（不把结论给仲裁者）、缺口归因（漏派 vs 漏报）、独立性闸门（指标变成开关）。
4. **工程**：Java 平台 116 测试、MySQL 8.4 迁移、Outbox + fencing、容器隔离、22 表备份校验和。
5. **边界**：没上线、没真实 webhook、容器不是 VM、高并发证据不足。

### 15 分钟版（技术答辩）

30 秒版 + 第四节架构图逐层讲 + 第五节六个支柱各 1 分钟 + 第六节三条控制面各 1.5 分钟 + 第七节实验数字 + 第八节边界。

## 二、三个必背的 STAR 故事

### 故事 1：MySQL 停机从挂死到快速失败

- **S**：双实例容量压测时，把 mysqld 杀掉，认证读接口和 `/actuator/health` 都超过客户端 15 秒超时。
- **T**：过载时系统必须快速失败，而不是拖死线程池。
- **A**：把 Hikari `connection-timeout` 收到 3000ms、`validation-timeout` 2000ms；复测。
- **R**：认证读 3.12s 返回 500，健康检查 3.17s 返回 503；重启 mysqld 后无需重启网关即恢复。证据：`capacity-and-faults.json`。

### 故事 2：为什么不用 Seata

- **S**：平台有「预算预占 → 执行 → 结算」的跨步骤一致性问题，直觉方案是分布式事务。
- **T**：既要一致性，又不能让长模型任务持有全局锁。
- **A**：本地事务 + Outbox + 消费幂等 + 对账；attempt/fencing 防止旧执行覆盖新结果；Seata 只作为独立实验验证协议本身。
- **R**：20 并发请求 × 100 token、上限 300 → 恰好 3 个被接受，不超扣（`task-budget.json`）；12 并发争抢只产生 4 条不同 claim（`reliable-dispatch.json`）。

### 故事 3：仲裁层不能只读结论

- **S**：仲裁器原本拿到双方的自然语言结论。
- **T**：要避免仲裁退化成「谁的结论更响」。
- **A**：改成结论剥离——只给指针、引用与可证伪条件，回原始证据重推三态信号；同时把真实模型仲裁也加了 `redact_statements`。
- **R**：离线剂量曲线：粘性 0→1 时错误裁决 0/48→24/48。真实模型（DeepSeek `deepseek-flash`）：结论可见 acc 0.79、错误多数被跟随 25%；结论剥离 acc 0.92、被跟随 8%；已修复版本上的假阳性从 1 例降到 0。两条未检出属模型能力限制。

## 三、预设追问与答案

| 追问 | 答案要点 |
| --- | --- |
| 「多智能体不是更好吗？」 | 实证相反：同源错误相关，收益来自信息不对称。引用 HIDDENBENCH 30.1% vs 80.7%。 |
| 「你们的创新是什么？」 | 不主张机制首创。差异三点：合成到代码审查的可运行协议、覆盖率补检闭环、独立性当闸门。 |
| 「33 rps 是什么意思？」 | 单机短时探针，**不是并发能力结论**；系统是异步任务平台，主指标是任务吞吐与过载行为，不是 QPS。 |
| 「为什么 Java + Python 两套？」 | 平台业务要强类型与事务；取证/聚合是研究型代码，迭代快。边界是版本化协议，不共享数据库写入。 |
| 「fencing 具体怎么做？」 | attempt 单调递增，写入时带 `WHERE attempt = :current`，旧执行影响 0 行即丢弃。 |
| 「幂等键怎么设计？」 | 由 `task_id + attempt + 输入摘要` 派生，落唯一索引；重复投递影响 0 行。 |
| 「有没有真实用户？」 | 没有。不给虚构的 QPS、用户数、准确率。 |
| 「模型实测数据呢？」 | 端点 403 停用，已如实记录为 blocked；工具与接线就绪，恢复后一条命令出数。 |
| 「为什么不用微服务？」 | 平台是模块化单体：事务边界清晰、运维成本低。拆分的收益在这里不成立。 |
| **「你们的召回率多少？」** | **必须带口径。** 同一批运行：25 行容差下读全 82%、5 行 59%、精确行 38%。所以我只讲**臂间排序**（读全 > 分散 > 集中，五档容差全部成立），不报单一百分比；精度未测（387 条 claim 只 48 条落在植入缺陷上）。 |
| **「多智能体比单 Agent 强吗？」** | 五切片对照：**2 胜 3 平 0 负**，均值 +0.6，符号检验 p≈0.25，**不显著**。可用论据是组合式：**同等质量 + 快 2.91 倍**。真正起作用的是「有界分批」而不是「多个 Agent」。 |
| **「共享同伴结论有什么用？」** | 没有质量收益（读全时 4/5 = 4/5；五切片召回 3 胜 2 平），但代价确定：冗余率 5/5 上升、K\* 5/5 下降。所以做的是**隔离**，不是共享。 |
| **「题目是不是太简单？」** | 我们专门造了难缺陷切片（E-9）：同 26 文件、12 条易缺陷换 5 条难缺陷。读全仍是 4/5，**没撞墙**；但逐条人工裁定比自动打分少 2 条（5/5 → 3/5）。真正的问在量尺，不在难度——所以我们把量尺规范成了 E-10 的容差曲线。 |

## 五、边界声明话术（主动说，别等问）

> 这个项目没有上线，也没有真实用户。隔离是容器不是 VM，共享宿主内核。高并发 只有单机短时探针，我不拿它当并发结论。真实 webhook 现场验收没做。三控制面里，结论剥离已有真实模型实测，缺口归因与闸门仍是规则替身/合成证据实验。代码 Apache-2.0，证据可复现。

## 六、不要说的话

- 不要说「首创信息分区 / 先独立后共识 / K*」。
- 不要说「高并发」「抗住 X QPS」。
- 不要说「准确率 / 召回率提升」。
- **不要不加口径地说「召回 92%」**：那是 25 行容差下的上界，精确行口径是 38%。要说「臂间排序」而不是单一百分比。
- 不要说「多智能体显著优于单 Agent」：5 片 2 胜 3 平，p≈0.25。
- 不要说「已上线」「生产可用」。
- 不要把秒杀、Seata 实验包装成平台核心功能。
- 不要拿 K*（输出指纹重叠）当正确性指标。
