## 一、作品定位

**Parallax 面向研发团队，提供从代码变更审查、证据追溯到人工批准修复和隔离回归的协作平台。Java 主导平台业务，Python 提供独立证据装配引擎，平台数据库统一采用 MySQL。**

参赛展示方向为开放原子大赛赛道一框架工具开发方向；具体报名名称及要求以官方通知为准。项目采用 Apache-2.0，保留可插拔框架、CLI、Receipt 协议及可复现评估。

本文所有数字均可回溯到 `eval/` 下的机器可读证据（见附录 A）。**未运行的环境、未产生的流量、未标注的准确率一律不写成本文结论。**

## 二、实际问题

多个同源模型给出相似结论，并不意味着获得了多份独立证据。2026 年的实证研究把这件事说得很清楚：

| 来源 | 结论 |
| --- | --- |
| HIDDENBENCH（arXiv 2505.11556） | 信息分散任务上多智能体 30.1%，单智能体拿到全量信息 80.7% |
| Correlated Errors in LLMs（ICML 2025） | 同源模型的错误高度相关 |
| Diversity Collapse（arXiv 2604.18005） | 根因是共享模型 + 共享 prompt 的结构耦合，过度收敛会漏掉非平凡缺陷 |
| InfoDelphi（arXiv 2607.01661） | 证据分区可降低误差相关性；移除信息不对称后增益几乎归零 |
| Audit Without Verification（arXiv 2609.07680） | 只读结论的问责层会退化成转发：只找回 4.1% 真因，删掉结论字段后升到 45.2% |

团队真正缺的不是「再来一个会说问题的模型」，而是：**依据可追溯、争议可保留、成本可控制、修复可验证。**

## 三、业务闭环

接入仓库 → 固定 commit/PR → 校验组织与项目权限 → 原子预占审查预算 → 可靠派发任务 → 独立取证/反证/聚合 → 展示 Claim 与来源 → 人工批准指定补丁 → 隔离回归 → 保存报告、补丁与审计记录。

## 四、技术架构

```text

                    身份 / 组织项目权限 / 仓库策略 / 任务状态机
                    原子预算预占与结算 / 报告 / 审批 / 审计 / 限流
                    MySQL 8.4（Flyway V1–V11）· Redis（Redisson / Bucket4j）
                    Outbox ──► RabbitMQ 4.1.4 ──► Python 审查 Worker

                                                        │
                                     隔离执行（子进程 或 容器，非 VM）
```

| RabbitMQ | 可靠派发、重试、死信 | **已验收**：真实 4.1.4 上 3 项集成；容器 broker 上 6 项投递语义 |

## 六、三条抗从众控制面（本轮新增）

多数多智能体系统止步于「我们度量了独立性」。本项目把三条控制面做成**可运行、可审计、会改变行为**的机制：

| 控制面 | 做什么 | 实测 |
| --- | --- | --- |
| **结论剥离仲裁** | 仲裁输入不含任何一方的结论文本，只给指针、引用与可证伪条件，回到证据重推三态信号 | 离线剂量曲线：结论粘性 0 → 1 时错误裁决 0/48 → 24/48；**真实模型（DeepSeek deepseek-flash）**：结论可见 acc 0.79 / 错误多数被跟随 25%，结论剥离 acc 0.92 / 被跟随 8% |
| **缺口归因** | 把「没覆盖到」拆成系统层漏派与读者层漏报，用 Chapman 估计漏检；无重捕不发数字 | 模拟 p=0.4/0.6/0.8 时估计相对偏差 −0.5%/−0.2%/+0.6% |
| **独立性闸门** | 独立性不足时自适应调整分区（重叠过高降冗余、通道不足加 Reader），用尽后把高置信降为待验证 | redundancy 1→3 时有效通道 3.00→1.00，`off/observe/enforce` 三态可切换 |

三条设计的共同纪律是**不确定就升级人工，不猜**：证据沉默时保留争议，无重捕时拒绝给漏检率，无法再提高独立性时不再空转。

**明确不主张**：信息分区（InfoDelphi）、冲突感知账本（LatticeMind）、结构化异议（FinCom）、同伴可信度估计（ECL）均已有 2026 年工作。本项目可核查的差异只有三点：①把上述认识合成到代码审查的可运行协议；②覆盖率驱动的补检闭环；③把独立性指标当作运行时闸门而非报表。

## 八、边界与未完成（必须如实说明）

1. **未公网部署**：无域名、无 TLS、无真实用户；本机验证与 Compose 配置不等于已上线。
2. **未做真实 webhook 现场验收**：GitHub/GitLab 接入逻辑已有离线与集成测试，真实仓库 + Secret 的端到端验证未做。
3. **隔离级别是容器，不是 VM**：共享宿主内核，敌对租户需专用 VM。
4. **高并发证据不足**：现有 33.92 rps 是单机短时探针结果，不含 soak、不含压测平台，**不作为并发能力结论**。
5. **三条控制面的证据强度不同**：缺口归因与闸门仍是规则替身/合成证据实验（方向性）；结论剥离仲裁已有真实模型实测（DeepSeek `deepseek-flash`，48 次调用 0 失败），但植入缺陷只检出 6/8，另 2 例是模型能力限制而非协议问题。
6. **派发全链路已验证，但不是多机**：broker → Java 消费 → Python Worker 进程的链路已在临时 broker 上跑通（含换进程、死信后恢复），但仓库内容与模型用的是确定性夹具；单机、单 broker 节点，不代表集群故障转移或模型质量。
7. **无人类评估**：没有真实团队的标注数据，不报告缺陷 precision/recall。
8. **E1 覆盖效应对照的边界**：语料是**固定规模采样子语料**（每片 26–32 个文件）。子采样按缺陷密度整组选取，会把密度抬高（某片 0.10 → 0.32），因此其**绝对召回率不可与全量运行比较**，只能用于两臂之间的对照；两臂差别仅在「三个 Reader 是否重复读同一批」，**收益来自联合覆盖，不来自更高的单文件精度**——范围分析显示集中臂漏掉的缺陷里绝大多数所在文件根本未被任何 Reader 读到；n=5 时双侧检验的最小可达 p 值为 0.0625，本项目假设有方向性，故按单侧报告并同时给出双侧值。
9. **「抗从众」的代价是独立性下降，不是召回下降**：E3b 显示共享同伴结论后冗余率升、有效独立通道 K\* 降（5/5 切片），但**召回没有变差**。因此「抗从众」应理解为「保护读者间的独立性与结论多样性」，**不得写成「共享会降低检出率」**。
10. **所有召回百分比都必须带口径，单看一个数字会误读**：评分口径是「同文件 + 行距 ≤ 25 行 + 断言为缺陷」。E-10 用同一批产物按 25 / 15 / 10 / 5 / 0 行重算，读全隔离从 82% 一路降到 38%，分散从 60% 降到 24%——**宽松口径整体高估 20~40 个百分点**。E-9 更直接：同一批运行自动打分 5/5，逐条人工裁定只有 3/5。因此本文只主张**臂间排序**与**相对优势**，不主张绝对召回率；凡是写出的百分比都同时给出口径。
11. **精确率已测，约 46%，不能宣称「准确」**：从 E1 的 113 条未匹配 claim 中固定种子抽 24 条，连源码逐条读：**真缺陷 11、明显不成立 7、合理加固建议 5、无法核实 1**，严格精确率 46%（Wilson 95% CI 28%~65%）。失败模式可归因：把设计取舍当缺陷、把正确的并发写法（锁内「查了再写」、条件 UPDATE）读错、locator 错位，以及一条自标 `critical` 却**可证伪**的误报（声称 `(?i)` 内联标志导致编译失败，而该模块 24 条测试全绿）。**因此本文仍不报告单一准确率数字，只声明已测且不高。**
12. **难缺陷无法把基线打到 60%~70%**：E-9 原本的假设是「换难缺陷后盲读基线会降到 60%~70%」，实测读全配置仍是 4/5，**假设不成立**。真正拉开差距的是 E-10 揭示的口径问题，不是缺陷难度。这一条推翻的是我们自己的假设，如实记录。
